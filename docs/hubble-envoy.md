# Hubble relay TLS and the Cilium envoy DaemonSet

Checked 26 Nov 2026 on Cilium 1.20.5. Both nodes stayed Ready. `https://hubble.lab.test/` returned 200 after the rollback below.

## What is wrong

Hubble relay's config has `disable-server-tls: true`. The UI talks to relay on port 4245 with no TLS. Relay's client connection to the agents is already TLS: the pod mounts `hubble-relay-client-certs`, and `hubble-disable-tls` in `cilium-config` is `false`.

Cilium also runs DaemonSet `cilium-envoy` on both nodes. `enable-l7-proxy` is true and `external-envoy-proxy` is true. The pods have no memory request or limit. One of them sits on the 4 GiB server.

## Safe change

Leave the agent dataplane alone.

Relay server TLS is the small piece. The chart value is `hubble.relay.tls.server.enabled`. It restarts `hubble-relay` and `hubble-ui` only. It does not roll DaemonSet `cilium`.

The envoy DaemonSet is not a safe removal. Argo CD's chart-name rules depend on the DNS proxy, and that proxy is the external envoy. Removing the DaemonSet restarts the dataplane and drops those lookups. A later change can set a memory limit on envoy without deleting it. That was not done here.

## Risk on this server

The server is 4 GiB and has already restarted k3s under memory pressure. A Cilium agent restart is a short dataplane blip on that node. An envoy restart is smaller but still on the same node. Do not combine either one with a Harbor or Grafana rollout.

## What was tried

`hubble.relay.tls.server.enabled: true` was applied. DaemonSet `cilium` did not roll. Relay started with `insecureServer:false` and then failed its peer handshake: `x509: certificate signed by unknown authority` while verifying `Cilium CA`. The relay stayed unready and the UI returned 503 until the old pod was gone. The value was reverted. Relay came back with `insecureServer:true`, connected to both nodes, and the UI returned 200.

Do not flip relay server TLS again until the relay client trusts the current Cilium CA. The certs are generated by the chart and are already in `ignoreDifferences`, so a render can fight a rotated CA.

## Validation if this is tried again

1. Confirm DaemonSet `cilium` does not roll. If it does, wait until both nodes are Ready before anything else.
2. `kubectl -n kube-system get deploy hubble-relay` is `1/1`.
3. The relay log says `Connected` for `k3s-server` and `k3s-agent`, with no CA error.
4. `curl -sk -o /dev/null -w '%{http_code}\n' https://hubble.lab.test/` is 200.
5. A pod DNS lookup still returns `10.43.0.1` for `kubernetes.default.svc.cluster.local`.
6. If the relay stays unready or the UI is not 200, set `hubble.relay.tls.server.enabled` back to false and sync again.
